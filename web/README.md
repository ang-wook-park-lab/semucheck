# 세무체크 웹 (컨설턴트용 진단 프로그램)

컨설턴트가 로그인해서 고객사를 등록하고, 분야별 체크리스트를 체크하면 **진단 보고서**(수임 판단, 개선 우선순위 TOP 5, 보완 로드맵, 추천 자금 매칭, 항목별 권고)가 만들어집니다. 보고서는 인쇄·PDF로 저장할 수 있습니다.

- 기술: Vite + React + TypeScript, 로그인·저장은 Supabase(선택)
- 체크리스트 데이터: 저장소 루트의 `../checklists/<분야>/*.json`을 그대로 읽습니다. 법령이 바뀌면 JSON만 고칩니다(코드와 데이터 분리).

## 실행

```bash
cd web
npm install
npm run dev      # http://localhost:5173
npm test         # 규칙 해석기·보고서 판정·체크리스트 데이터 계약 테스트
npm run build
```

## 로그인·저장 방식 세 가지

| 모드 | 조건 | 동작 |
|---|---|---|
| 서버 DB | 배포 서버에 `DATABASE_URL`(Postgres)이 있음 | 이메일/비밀번호 로그인(HttpOnly 쿠키 세션), 고객사·진단을 Postgres에 저장. 컨설턴트별 데이터 분리. 설정은 `../docs/deploy.md` |
| Supabase | 빌드 때 `VITE_SUPABASE_URL`·`VITE_SUPABASE_ANON_KEY`가 있음 | 이메일/비밀번호 로그인, Supabase 저장(행 단위 보안, RLS). 둘 다 있으면 Supabase가 우선 |
| 데모 모드 | 위 둘 다 없음 | 계정·고객사·진단이 **이 브라우저의 localStorage에만** 저장됩니다. 화면 확인용이며 보안 수단이 아닙니다. |

서버 DB 모드는 프런트가 실행 중에 `/api/health`로 자동 감지합니다(`src/lib/auth.tsx`). `npm run dev`에는 API가 없어 데모 모드로 뜹니다. DB까지 붙여 확인하려면 `npm run build` 후 `DATABASE_URL=... npm run serve`를 쓰세요.

### Supabase 설정
1. Supabase 프로젝트를 만들고 SQL Editor에서 `supabase/schema.sql`을 실행합니다.
2. Authentication에서 이메일 로그인을 켭니다. 가입 확인 메일을 쓰지 않으려면 "Confirm email"을 끕니다. 컨설턴트 계정을 제한하려면 가입(Sign ups)을 끄고 관리자가 초대하세요.
3. `.env.example`을 `.env`로 복사하고 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`를 채웁니다. anon 키는 공개용이며, 데이터 보호는 RLS가 맡습니다. **service_role 키는 절대 넣지 마세요.**

### Vercel 배포
- Root Directory를 `web`으로 지정하고 "Include source files outside of the Root Directory"를 켭니다(`../checklists`를 읽기 때문).
- 환경변수 `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`를 설정합니다. SPA 라우팅은 `vercel.json`이 처리합니다.

## 화면 구성
홈(현황·분야 선택) → 진단 시작(고객사 선택/등록) → 체크리스트 작성(카테고리별, 자동 저장, 문항별 메모) → 보고서 → 진단 내역. 고객사 정보(업력·근로자·법인 여부·연구소·벤처)에 따라 해당 없는 문항은 자동으로 빠집니다(`applies_if`).

## 법인 일반관리 64항목 점검 (○△×— 방식)
정책자금 진단처럼 규칙으로 위험을 판정하지 않고, 컨설턴트가 항목마다 ○양호 / △보완필요 / ×미흡 / —해당없음을 직접 고르는 점검표입니다(책 76장 그림 16부-3의 서식).
- 데이터: `../checklists/corporate-general/general-64.json` (8영역 × 8항목), 형식은 `../schema/status-checklist.schema.json`
- 작성 화면: 영역별 카드 8개, 항목 이름을 누르면 점검 포인트·보완 권고·메모, 하단에 결과 요약·종합 코멘트·개선 우선순위 TOP 5·다음 점검 계획
- 보고서: 영역별 막대, 관리 수준(양호 1점, 보완필요 0.5점, 해당없음 제외), 미흡·보완필요 상세와 권고
- 판정: 점검 60% 미만이면 보류, 위험도 높은 항목이 미흡이면 "즉시 개선 필요", 미흡·보완필요가 있으면 "보완 필요", 없으면 "양호"
- 개선 우선순위: 미흡이 보완필요보다 먼저, 같으면 위험도(high → low), 같으면 책의 영역·항목 순서
- 점검 포인트·권고·위험도·근거 조문은 시제품 초안입니다(`verified_at` 비어 있음). 스캔이 흐린 문구 2곳은 `ocr_uncertain`으로 표시했습니다.

## 노무 진단 (89문항)
`../checklists/labor/labor-diagnosis.json` — 취업규칙 개정·신고 / 근태·연차 관리 / 괴롭힘·성희롱 대응 / 징계·해고·권고사직 / HR 경영보고(KPI) / 기본 노무 관리 6개 카테고리. 정책자금과 같은 위험 규칙 방식이며, 분야별 용어만 다릅니다(정책자금: 결격·감점·가점, 노무: 위반 위험·보완 필요·모범 사례. `src/lib/checklists.ts`의 `labels`).
- 고객사의 **상시 근로자 수**로 적용 문항이 갈립니다: 취업규칙·괴롭힘 규정은 10명 이상, 연장·연차·해고 제한 등은 5명 이상.
- 질문 하나(예: 취업규칙 개정 중인지, 해고 검토 대상이 있는지, 근로시간 제도 종류)로 후속 문항이 나타나거나 사라집니다(`applies_if`).
- 법령 근거와 `[실무자 확인 필요]` 표시는 문항의 `legal_basis`·`consequence`에 있습니다. 설명 자료는 `../knowledge/labor/`.

## 회계 진단 (74문항)
`../checklists/accounting/accounting-diagnosis.json` — 장부·증빙 / 부가가치세 / 결산·재무제표 / 재무 리스크·신용 연계 / 법인세·세무조정 / 원천세·급여·4대보험 / 특수관계·자금 거래 / 세무조사·절세 대비 / 개인사업자 기본. 노무와 같은 위험 규칙 방식과 같은 분야 용어(위반 위험·보완 필요·모범 사례)를 씁니다.
- 고객사의 **사업자 형태**(법인/개인)와 연구소 보유 여부로 문항이 갈리고, 가지급금 유무·업무용 승용차·영세율 거래·특수관계 거래 같은 질문에 답하면 후속 문항이 나타나거나 사라집니다.
- 노무는 사용자 제공 지침이 근거였지만 **회계는 제공 지침 없이** 저장소의 기존 정리(정책자금 도서의 결산·5대 위험 항목·세무)와 회계·세무 일반 지식으로 작성한 초안입니다. 근거는 문항의 `source`, 확인이 필요한 사항은 `[실무자 확인 필요]`로 표시했습니다. 설명 자료는 `../knowledge/accounting/`.

## 판정 규칙 (정책자금, 책 63장 기준)
- **수임 불가**: 세금 체납(FUND-001), 신용불량·회생·파산(004), 자본잠식(005), 진행 중 소송(006) 중 하나라도 해당
- **지금은 신청 불가**: 그 밖의 빨강(결격) 문항이 해당
- **즉시 수임**: 빨강 0 + 대표 신용 5등급 이내 + 매출 증가 + 자금 목적 명확 + 인증 1개 이상
- **준비 후 수임**: 빨강 없음, 나머지(3개월 로드맵)
- 응답이 전체의 60% 미만이면 판정을 보류합니다. 분야가 정책자금이 아니면 빨강/노랑 개수로 일반 판정만 합니다.
- 보완 로드맵: 빨강=즉시, 노랑 중 중요도 high=3개월 이내, 나머지 노랑=결산 전, 파랑=인증·특허 순서(이 구간 나누기는 시제품 가정입니다).
- 체크리스트 문항 형식과 `risk_rule`/`applies_if` 문법은 `../schema/checklist-item.schema.json`과 `src/lib/rules.ts`를 보세요. `eval`은 쓰지 않고 지원 문법만 해석합니다.
